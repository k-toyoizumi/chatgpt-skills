# Model and Cost Rules

## モデル系列の既定方針

通常作業は **Terra / Luna** を基本とし、**Solは全体の本質的な計画と批判的レビューに限定**する。親Agent・サブエージェント・再試行・フォールバックに共通して適用する。

- 全体の本質的な計画は、目的・制約・成功条件・構成・重要なトレードオフを決める作業を指す。既定方針に沿う手順化・小修正の段取りは通常作業とする。
- 批判的レビューは、前提・論理・設計・評価の弱点や反証・代替案を検討する作業を指す。形式チェックや通常の動作確認は通常作業とする。
- 実装・検索・抽出・要約・通常の分析・検証はTerra / Lunaで行い、難しいことや失敗したことだけを理由にSolへ切り替えない。Solが必要なら上記の判断・レビュー部分だけを切り出す。
- Terra / Lunaが利用できない場合もSolへ無断でフォールバックせず、利用可能な設定と代替案を示して相談する。
- この方針はSolのhigh以上や他の制限対象モデルの実行承認を含まない。既存の明示的な事前承認制限を維持する。

モデル系列の方針と、実行可能な具体的モデル識別子を区別する。世代・識別子・対応effortは固定せず、実行環境で確認してプランへ明記する。Terra等の未確認の識別子を捏造しない。

具体的なモデル名の対応表は、実行時設定・プロジェクト設定・短命なmappingとして管理する。文書の更新だけで稼働中Agentのモデルやサービス側設定を変更したと扱わない。

## Model / reasoning effort

### TerraとLunaの使い分け

次は本リポジトリの運用基準であり、同じ系列でも世代をまたぐ性能・料金の優劣を保証するものではない。

| 系列 | 担当の目安 | effortの出発点 |
| --- | --- | --- |
| Luna | 入出力と成功条件が明確な抽出・分類・要約、限定的なコード修正、定型的な検証 | low。必要な場合だけmedium |
| Terra | 複数ファイル・資料の文脈を扱う通常実装、原因調査、比較・統合など、Lunaでは分割や手戻りが増える作業 | low〜mediumの必要十分な値 |
| Sol | 本質的な全体計画・批判的レビューのみ | low〜medium。既存の承認制限に従う |

- 明確で限定的なタスクはLunaを優先し、文脈間の依存や判断の多い通常作業はTerraを選ぶ。Lunaで品質不足なら原因を確認し、作業分割・入力改善またはTerraへの変更を検討する。
- 利用可否は「公式の提供情報」「PCのモデル一覧・設定」「今回の起動ツールで指定可能なモデル」「実行成功」を区別する。キャッシュにあるだけで、その会話から起動できると断定しない。
- 通常モデルが一方しか使えない場合は、そのモデルで品質を満たせる範囲を担当させる。満たせない場合は代替を相談し、存在しないモデル名やSolへの無断切替で補わない。
- 選定の背景：[Terraの公式説明](https://developers.openai.com/api/docs/models/gpt-5.6-terra)、[Lunaの用途とモデル提供情報](https://learn.chatgpt.com/docs/models)。最新の提供・料金・対応effortは利用時点で確認する。

### 作業別の目安

原則として、必要十分な最小構成から開始する。

| 処理 | 推奨 |
| --- | --- |
| LLM 不要 | 通常コード / 通常ツール |
| 日常質問・検索・抽出・限定範囲の要約 | Terra / Luna + low |
| 実装・通常の分析・原因調査・検証 | Terra / Luna + low〜medium |
| 全体の本質的な計画 | Sol + low〜medium |
| 前提・論理・設計・評価の批判的レビュー | Sol + low〜medium |

対応するeffortのうち必要十分な最小値を選ぶ。上位effortが必要でも、既存の事前承認制限を越えて実行しない。

検索・Web 参照が不要な日常質問では、不要な外部検索を行わない。

### Escalation

- UI polish、単純同期、機械的変換だけを理由に high へ上げない。
- 失敗時は全体を高 effort でやり直さず、失敗箇所だけ escalate する。
- 大量の独立タスクへ自然に分割できる場合だけ multi-agent を検討する。
- Agent を増やすこと自体を目的にしない。

## プランでの委譲設計と再利用

- プラン立案を依頼されたら、親Agentが担当する作業とサブエージェントへ委譲する作業範囲を分ける。各委譲先の対象・成果物・完了条件、具体的なモデル識別子と reasoning effort、新規作成／既存再利用をプランに明記する。能力区分だけの指定や暗黙のモデル継承で済ませない。
- 利用可能なモデル・effortと許可範囲を実行環境で確認し、必要十分な最小構成を選ぶ。確認できない設定は「未確認」とし、仮の候補と実行可能な設定を区別する。プランへの記載を実行・昇格の承認と解釈せず、既存のモデル利用制限を維持する。
- 新規起動時はモデル・effort・担当を明示指定して固定する。再利用時も確認済み設定を維持し、暗黙の継承・昇格をしない。設定変更が必要なら実行環境の対応と承認を確認する。
- 作業範囲・難易度が似ていて、モデル・effort・権限・既存Contextが適合する場合は、同じサブエージェントへの追加依頼を優先する。稼働中の別担当を上書きせず、同じAgentが担う依存作業は順次実行する。
- 再利用か新規作成かは、引き継ぎ情報量、蓄積Context、並列化の必要性、独立レビューの必要性を含めて判断する。無関係な履歴が大きい場合や設定が不適合な場合は新規作成を選び、再利用自体を目的にしない。
- 再利用方針・選定理由・再利用できない場合の代替をプランに含める。実行時は既存Agentの識別子と確認済みモデル・effort・担当を案件側で管理する。Sessionをまたぐ存続・再開可否を推測せず、利用可能な場合だけ再利用する。
- 新規Agentへの入力は目的・制約・必要な資料に絞り、再利用Agentには変更点と必要な参照だけ渡す。結果は成果物・検証・未解決点に絞って受け取り、親と子で同じ作業を重複実行しない。
- 通常ツールや親Agentだけで十分な小作業では「委譲なし」と理由を示す。計画のためだけにAgentを起動しない。クレジット・トークンの削減量は実測なしに断定せず、取得できる利用量と手戻りから運用を見直す。

## Research routing

論文・技術調査では、調査フェーズごとに必要な reasoning depth が異なる。

詳細な手順は `skills/research-survey/SKILL.md` に置き、ここでは routing 原則だけを定義する。

| Phase | 主目的 | 推奨 |
| --- | --- | --- |
| pre-survey | 調査観点・仮説・検索軸の設計 | 通常はTerra / Luna。本質的な全体計画の部分のみSol |
| quick-and-wide-survey | 多数候補を広く収集・一次選別 | Terra / Luna + low〜medium |
| deep-research | 文献の読解・統合・比較・分析 | Terra / Luna。批判的レビューの部分のみSol |

pre-survey は、調査目的・観点・検索語が十分明確な場合は省略してよい。単純な整理だけで済む場合は low まで下げてよい。

quick-and-wide-survey では、metadata 整理、重複排除、タイトル・abstract の抽出、候補表作成など、決定論的に処理できる部分は通常ツール・コードを優先する。

## Prompt Cache を意識した Context 設計

API / Agent 実装で cache を制御できる場合は、安定部分と変動部分を分離する。

### Stable prefix

- 共通 instructions
- 固定 schema
- 安定した tool definitions
- 長期 reference

### Variable suffix

- 今回のユーザー指示
- 日時
- 最新検索結果
- 変更データ

### ルール

- tool 定義の順序・schema を不用意に変えない。
- 一時的な検索結果や時刻を stable prefix に入れない。
- cache の料金・lifetime・対応 model は、利用時点の公式仕様を確認する。
- ChatGPT アプリ内部の hidden prompt / cache hit を、ユーザー側で制御できる前提にしない。
