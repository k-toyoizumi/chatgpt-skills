# Git Workflow

判断基準は `rules/git-workflow.md`、検証原則は `rules/change-and-validation.md` を参照する。これらの相対パスは正本リポジトリを起点に解決する。Git操作の権限はユーザーの最新指示と既存の合意から判断する。

## 1. 作業前の確認

- `git status --short --branch`、`git diff`、`git diff --cached` で作業開始時の変更を確認する。未追跡ファイルは必要なものだけ内容を読む。
- 現在のブランチ、upstream、remoteの送信先、直近のコミット規約を確認する。認証情報を含むURLは出力・報告で伏せる。
- 小さな個人作業は現在のブランチ、共同作業・大きな変更は作業ブランチ＋PRとする。detached HEADではローカルブランチとの対応と作業目的を確認し、既存ブランチへ安全に戻すか作業ブランチを作る。対応が不明なら相談する。
- プッシュで実行される既知のCI・デプロイと合意範囲を確認する。全設定の監査を毎回行う必要はない。

## 2. 変更の選別・検証

- 作業開始時の変更と今回の変更を分離する。同じファイルに混在する場合は部分ステージングを検討し、分離困難なら相談する。
- 目的ごとにファイルまたはhunkを選び、`git add -- <path>` や `git add -p -- <path>` でステージする。既存のindexを一括リセットしない。
- `git diff --cached --stat` と `git diff --cached` で対象全体を確認し、`git diff --cached --check` と変更内容に応じた既存チェックを行う。新規・未追跡ファイル、機密情報、不要な生成物も確認する。
- 部分ステージングや未ステージの依存変更がある場合、作業ツリーのテスト成功をコミット内容の検証済みとは扱わない。必要に応じて一時ディレクトリへindexの内容を取り出し検証する。検証後に変更した内容は影響箇所を再検証する。

## 3. コミット

- 最新の指示で許可されていれば、確認したindexを `git commit` で記録する。ファイル指定や `-a` による対象のすり替わりを避ける。
- `rules/git-workflow.md` の言語・形式方針に従い、件名・本文を日本語で、変更の目的が分かるメッセージにする。既存履歴が英語という理由だけで英語を継続しない。hook失敗は原因を修正して再検証し、無断で `--no-verify` を使わない。
- `git show --stat --oneline HEAD` と必要な差分で結果を確認する。hookによる変更や意図しない取り込みがあれば、履歴を無断で書き換えず対処する。

## 4. プッシュ・必要なPR

- 対象remoteをfetchし、送信先ブランチとの差分・ahead/behind・未送信コミットを確認する。新規ブランチなら予定のPR先との差分も確認する。fetch失敗時は最新状態を確認済みと報告しない。
- 過去の未送信コミットも送られるため、合意範囲外の履歴が含まれる場合は送信せず相談する。remoteが進んでいる・履歴が分岐している場合は、変更範囲と統合方針を確認する。
- 送信先を明示した `git push <remote> HEAD:refs/heads/<branch>` を基本とし、新規ブランチで必要なら `-u` を付ける。`--all` / `--mirror` / `--tags` を通常の成果反映に使わない。
- 拒否・認証失敗・保護ルール違反は原因を確認し、強制送信や設定変更で回避しない。通信結果が不明ならremoteのrefを読み直し、成功・失敗を確認してから再試行する。
- 作業ブランチ＋PRの運用では、既存PRを確認して更新し、なければ利用可能なGitHubツール等でPRを作成する。マージは別の合意に従う。
- push結果とremoteの対象refを確認する。CIを確認した場合も「送信成功」と「CI成功」を区別する。

## 完了報告

変更の要点、検証結果、コミットID、送信先ブランチ、必要ならPR URLを簡潔に示す。残る未コミット変更や未実行・失敗した操作があれば、今回の成果と区別して報告する。
