# Long-running compute

共通方針は正本ルートから `rules/core.md` と `rules/change-and-validation.md` を参照する。実行記録と固有のコマンドは対象プロジェクトに置く。

## 1. 実行範囲を決める

- 今回が動作確認か本番の学習・評価かを区別し、既存の実行手順・許可範囲・資源上限・停止条件を確認する。既に承認された範囲は再質問しない。このSkillの導入だけで新しい実験・課金・上限拡大を承認済みとしない。
- 同じ処理の既存ジョブと保存済み状態を確認し、重複起動を避ける。状態不明なら追加起動せず照合する。

## 2. 数件で動作を確認する

- 未確認または変更した実行経路は、代表的な数件（例：2〜5件）で入出力・主要経路・ログ・成果物を確認する。件数だけでなく学習ステップ・エポック・試合数等も必要十分に小さくし、時間上限を設ける。
- 件数制限が前処理にも効いているかを確認し、確認のために全件ロードや全件評価を走らせない。少数実行の設定・出力を本番と区別する。
- 同じ版・設定の経路で既に十分確認済みなら重複実行しない。失敗時は原因箇所を修正して少数件で再確認する。
- 動作確認だけの依頼ならここで終了する。少数件の成功を性能評価や全件検証の完了とせず、本番計算は依頼範囲に含まれる場合だけ起動する。

## 3. WSLでバックグラウンド起動する

- 既存のジョブ管理基盤を優先し、なければtmuxやnohupと必要に応じたsetsid等から環境に合う方法を選ぶ。ツールの一時セッションIDや単なる `&` だけを会話終了後の継続保証としない。
- 作業ディレクトリ、仮想環境、実行コマンド、上限、ログ・成果物の保存先を固定し、標準入力を切り離し、標準出力・標準エラーをファイルへ保存する。終了コード・終了時刻も後から判別できる形にする。
- 実行IDまたはPIDと起動時刻、コード版・設定を案件側へ記録する。プロセス群を起動する場合は、対象ジョブだけを停止できる方法を確認する。

## 4. 起動確認と引き継ぎ

- 起動直後だけ短く、実行状態と初期ログを確認する。即時失敗は失敗として扱い、再試行は許可範囲・上限内で原因を解消して行う。既に終了していれば終了状態と成果物を確認する。
- 実行中なら実行ID/PID、ログ・成果物の場所、状態確認・停止の具体的なコマンドを記録し、回答で共有する。確認していない完了・成功は報告しない。
- 他に作業がなければ、計算終了まで待つだけのポーリングを続けず応答を終了する。他の独立した依頼作業があれば進める。
- 完了監視・通知は依頼された場合に設定し、設定成功を確認する。バックグラウンド起動だけで通知を約束しない。PC停止・WSL終了後の継続や再開は、実際の仕組みを確認せず保証しない。
