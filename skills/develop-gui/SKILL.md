# 対話で進めるGUI開発

## 目的と位置づけ

ユーザーの確認負担・実装待ち・手戻りを減らす。厳密な仕様書を先に完成させることを目的にせず、次の小さな試作に必要な判断だけ合意する。
このSkillは設計対話とGUI品質確認を担当する。実装・公開には対象環境のSkillと既存プロジェクトの規則を併用し、最新のユーザー指示を優先する。既存の承認や決定を聞き直さない。

研究業務のGUIでは `research-dialogue` を併用する。その場合、研究上の壁打ちは通常3〜5問ずつとし、説明を求められた質問は説明後に聞き直す。本Skillの一般GUI向けの質問量より研究対話の合意を優先し、同じ質問を重ねない。

## 1. 現状と不確実な点を把握する

- 依頼、既存コード・画面、利用できるサンプル、決定済み事項を必要な範囲で確認する。既存GUIの改善では、可能なら変更前の実画面を操作・撮影する。
- 目的、代表的な利用場面、入力と期待する出力、対象端末、今回の範囲を把握する。依頼から分かる内容を質問し直さない。
- 仕様が明確で小さな修正なら、質問や2案比較を省いて実装する。

## 2. 重要な点だけ選択式で壁打ちする

- 誤ると大きな作り直しになる判断だけ先に質問する。目的、主要な操作、結果の意味・計算、保存や外部連携、実データと仮データの境界などを優先する。
- 軽微で戻しやすい配置・装飾や実装の詳細は、既存の慣習と合意に沿って決める。推測した事項をユーザーの決定として記録しない。
- 質問は簡潔で具体的にし、利用時の違いで選べるようにする。通常は1問ずつ、関連する短い質問なら最大3問までまとめる。固定の質問票を消化しない。
- 通常2〜3の選択肢を用意し、根拠のある推奨案には「推奨」と短い理由を付ける。自由入力、お任せ、まだ分からないという回答も受け入れる。
- 併用できる好み・要望は複数選択、相互に両立しない決定は単一選択にする。利用可能な選択式UIを用い、無ければ番号付きの短い質問にする。
- 画面を見た方が判断しやすい点は、文章で質問を重ねず次の画面比較へ移る。研究上の不確実さは小さな試作で確かめる。

## 3. 大きな変更だけ、実画面案を2つ見せる

- 新規アプリ、配置・操作の大幅変更では、主要画面の異なる2案を提示して選んでもらう。小さな変更には比較を強制しない。
- 画面案は閲覧可能なモックや軽い試作として示す。長文やワイヤーフレームの説明だけで代用しない。対話内のプレビューに対応した環境では適切な可視化機能を使う。
- 同じ代表的な内容・データで比べ、2案の差を一言で示す。配置や操作を比べる場合は差を明確にし、色だけを比べる場合は構造を揃える。架空の数値はサンプルと明示する。
- 「両方の一部を組み合わせる」「どちらも違う」も受け入れる。選ばれなかった案の本実装を進めない。

## 4. 好みを用途に合わせて適用する

- 共通の初期方針を、青系のアクセント、明確な情報の区切り、大きめの角丸とする。主要な情報と操作を先に見せ、詳細は必要時に開く。
- 見た目の好みをアプリの用途に合わせて調整し、ユーザーが明示したデザインや既存アプリの一貫性を優先する。既存GUIを無関係な修正のついでに改装しない。
- 主操作、結果、状態を見分けやすくし、色だけで意味を伝えない。詳細を畳んでも主要な比較や頻用操作を妨げない。

## 5. 作業に合う確認の区切りを提案して実装する

- 回答と画面選択を踏まえ、「今回作るもの・仮で済ませるもの・完成条件」を数行で共有する。全文仕様書の確認を一律に求めない。
- 規模と不確実さに合わせて確認の区切りを提案する。小修正は検証まで一続き、大きな変更は代表的な作業が一つ通る段階などを候補にする。
- 合意した区切りで確認を求める。区切りの間は軽微な判断や修正を自律的に進める。新たな重要判断が生じたときだけ選択式で戻す。
- 既存部品と実装を再利用し、合意した範囲に限定する。不要な機能・依存・全面改修を追加しない。試作では品質への寄与が薄い設計やテストを増やさない。

## 6. ユーザーに渡す前に自分で確認する

- 対象GUIを起動し、代表的な入力→操作→結果を実画面で確かめる。ビルド成功だけで完成としない。
- 実行中のGUIのスクリーンショットを撮影し、画像を実際に開いて、文字切れ、重なり、読みにくさ、操作の分かりにくさ、合意した画面案との差を確認・修正する。撮影しただけで確認済みとしない。
- 変更に影響される既存機能と主要導線を確認する。機械的に判定できる計算・保存・状態などは適切なテストや通常コードで確かめ、見た目の自己評価だけに依存しない。
- 対象端末・画面サイズで確認する。スマホとPCの両方を毎回必須にはせず、依頼と対象アプリの利用条件に合わせる。
- Webなら利用可能なブラウザ自動操作、ネイティブGUIなら利用可能なGUI操作・撮影手段を使う。未対応なら不足を短く伝え、実行可能な確認だけ行う。未実施を成功と報告しない。
- 問題箇所を限定して修正・再確認する。同じ失敗が続く場合は原因と次の選択肢を示す。新しい問題がないのに全体の再検証や見た目の磨き込みを繰り返さない。

## 7. 短く引き渡し、決定を残す

- 実画面または短い操作動画などの確認材料とともに、変更点、確認結果、重要な未確認事項だけ短く報告する。
- プロジェクト固有の決定・次の確認点・検証結果は、そのプロジェクトの状態管理先に差分で残す。以後の対話で同じ内容を再質問しない。
- 本Skillや過去の公開承認を、新しい公開先・外部送信・権限変更への包括的な許可として扱わない。必要な公開は既存の許可範囲と環境の規則に従う。
